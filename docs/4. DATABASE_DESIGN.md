# AteThat — Database Design by Phase

## Phase 2.6 — occurrence rescheduling audit

`health_item_events.version` guards stale actions; `rescheduled_to_utc` is the effective scheduled instant while original schedule fields/identity remain immutable. Owner/date indexes support moved-range projection. New `health_item_event_history` snapshots before/after each successful action in the same transaction, uniquely indexed by user, occurrence and revision. The account purge includes these snapshots. Legacy RESCHEDULED markers are interpreted on read; no destructive migration is needed.

## Phase 2.5 — local additive schema

Target values additionally retain applicable range bounds, selected energy basis, source URL/revision, outside-reference status, acknowledged UTC instant (Mongo millisecond precision) and a confirmation hash. Signed review tokens are short-lived and not stored as credentials. Initial proposals store a profile/calculation fingerprint; new revisions preserve historical inputs and confirmations. No destructive migration is required.

`nutrition_target_versions` retains its existing owner/status/revision model. New optional `input_snapshot` holds effective height/weight/activity, assumption flags, age/sex when supplied and profile-saved timestamp. Selected target entries gain `provenance` (`CUSTOM`/`MACRO_DERIVED`/`CALCULATED_DEFAULT`; legacy rows derive their label from `is_manual_override`). No migration/backfill overwrites old records. Custom saves create a new ACTIVE revision and supersede the previous one in one transaction, guarded by active ID/revision and profile version. Untouched Decimal128 values are copied, not reconstructed from display rounding. A profile review marker serializes concurrent profile/target saves; it does not update measured weight.

Missing-input constants are not persisted as measurements. Wellness records never modify profile weight. Factual Text Summary is an ephemeral authorized projection over existing collections; neither generated text nor edited browser drafts get a new collection or browser-persistent storage. See [Phase 2.5 status](PHASE_2_5_STATUS.md) for verification and remaining scope. Calculated resets store PERSONALIZED_ESTIMATE basis, versioned source/calculation metadata and effective input snapshots; no preview collection is created. SHA-256 fingerprints are recomputed from owner, profile version, inputs and canonical server-calculated values during the reset transaction.

## Phase 1 — released storage baseline

### 1. Purpose

This document defines how AteThat stores Phase 1 data in MongoDB. It specifies collection boundaries, exact BSON types, representative documents, indexes, TTL rules, ownership rules, transaction boundaries, immutable-history behavior, and pagination support.

The examples use MongoDB Extended JSON so types are unambiguous:

```json
{
  "object_id": { "$oid": "66f7e68012ab34cd56ef7890" },
  "instant_utc": { "$date": "2026-09-27T20:10:00.000Z" },
  "decimal_value": { "$numberDecimal": "72.50" }
}
```

Application JSON sent over REST remains ordinary JSON. Extended JSON examples are representative design shapes, not exact dumps or proof that every illustrated `schema_version`, validator or index exists. Runtime BSON structs and store index initialization determine the actual persisted shape; reconcile migrations against them before execution.

### 2. Database-level decisions

#### 2.1 Database names

Use a separate database for each environment:

```text
atethat_dev
atethat_test
atethat_prod
```

If multiple projects share a MongoDB Atlas cluster, every project receives a different database and a different least-privilege database user. RollerCoaster, for example, must not share AteThat's database credentials or collections.

#### 2.2 Identifiers

- MongoDB `_id` fields use BSON `ObjectId`.
- References such as `user_id` and `food_log_group_id` are stored as BSON `ObjectId`, not strings.
- IDs crossing the REST boundary use the 24-character hexadecimal ObjectId representation.
- External identifiers, such as a USDA food ID, remain strings because they are owned by another system.
- Security never depends on IDs being difficult to guess; every query enforces authenticated ownership.

#### 2.3 Instants, dates, local times, and timezones

- Actual instants use BSON `Date` and are always normalized to UTC.
- Date-only values use strings formatted as `YYYY-MM-DD`.
- Local time-of-day values use strings formatted as `HH:mm` using a 24-hour clock.
- User timezones use IANA identifiers such as `Asia/Kolkata`.
- Tracking Day uses a date-only string because it is a user-local business date, not an instant.
- Recurrence definitions store local wall-clock rules plus their IANA timezone. Generated occurrences store UTC instants.

The database server timezone and application-host timezone are never used to interpret user data.

#### 2.4 Decimal values

Nutrition, quantity, height, weight, and other calculation-sensitive numbers use BSON `Decimal128`.

Do not use BSON `double` for nutrition calculations. The Go persistence layer converts between domain decimal types and MongoDB `Decimal128`.

#### 2.5 Common document fields

Most mutable documents contain:

```json
{
  "schema_version": 1,
  "version": 1,
  "created_at": { "$date": "2026-09-27T20:10:00.000Z" },
  "updated_at": { "$date": "2026-09-27T20:10:00.000Z" }
}
```

- `schema_version` identifies the stored-document format.
- `version` supports optimistic concurrency.
- Immutable event/snapshot documents may omit `updated_at` and `version`.

### 3. Ownership and repository rules

Every user-owned collection contains `user_id: ObjectId`.

Repository methods require `user_id` separately from the resource ID:

```go
GetFoodLogGroup(ctx, userID, groupID)
UpdateProfile(ctx, userID, expectedVersion, update)
ListHealthItems(ctx, userID, page)
```

The repository filter must contain both values:

```javascript
{
  _id: ObjectId(groupID),
  user_id: ObjectId(authenticatedUserID)
}
```

The API never accepts `user_id` from a request body as authority. MongoDB does not provide application-level foreign-key enforcement, so Core validates references and uses transactions where cross-document consistency matters.

### 4. Canonical nutrient format

Nutrients are stored as an object keyed by canonical nutrient code. This prevents duplicate nutrient codes and supports adding nutrients without changing the document schema.

```json
{
  "nutrients": {
    "ENERGY": {
      "status": "KNOWN",
      "amount": { "$numberDecimal": "310" },
      "unit": "kcal"
    },
    "PROTEIN": {
      "status": "KNOWN",
      "amount": { "$numberDecimal": "12.0" },
      "unit": "g"
    },
    "VITAMIN_D": {
      "status": "UNKNOWN",
      "amount": null,
      "unit": "mcg"
    }
  }
}
```

Rules:

- `status` is `KNOWN` or `UNKNOWN`.
- `amount` is required for `KNOWN`; `UNKNOWN` has no numeric amount. Depending on the stored struct it may be omitted rather than persisted as BSON null; never store zero to represent unknown.
- A verified zero is `{ "status": "KNOWN", "amount": 0 }`.
- Units use canonical lowercase or case-sensitive symbols defined by the application, such as `g`, `mg`, `mcg`, `ml`, and `kcal`.
- Calculations normalize compatible units before aggregation.
- Snapshot documents also store the normalization/calculation version.

### 5. Identity collections

#### 5.1 `users`

Purpose: account identity and lifecycle. Password material is deliberately excluded.

```json
{
  "_id": { "$oid": "66f7e68012ab34cd56ef7890" },
  "email_normalized": "archit@example.com",
  "email_display": "Archit@example.com",
  "email_verified_at": { "$date": "2026-09-27T20:15:00.000Z" },
  "status": "ACTIVE",
  "schema_version": 1,
  "version": 2,
  "created_at": { "$date": "2026-09-27T20:10:00.000Z" },
  "updated_at": { "$date": "2026-09-27T20:15:00.000Z" }
}
```

Enums:

```text
status: PENDING_EMAIL_VERIFICATION | ACTIVE | PENDING_DELETION | DISABLED
```

Indexes:

```javascript
db.users.createIndex({ email_normalized: 1 }, { unique: true })
db.users.createIndex({ status: 1, created_at: -1 })
```

#### 5.2 `auth_identities`

Purpose: credential data separated from the public account record.

```json
{
  "_id": { "$oid": "66f7e6a712ab34cd56ef7891" },
  "user_id": { "$oid": "66f7e68012ab34cd56ef7890" },
  "identity_type": "LOCAL_PASSWORD",
  "password_hash": "$argon2id$v=19$m=65536,t=3,p=2$BASE64_SALT$BASE64_HASH",
  "password_changed_at": { "$date": "2026-09-27T20:10:00.000Z" },
  "schema_version": 1,
  "created_at": { "$date": "2026-09-27T20:10:00.000Z" },
  "updated_at": { "$date": "2026-09-27T20:10:00.000Z" }
}
```

For a Google identity, the document instead contains `identity_type: "GOOGLE"`, `provider: "GOOGLE"`, and the provider's stable OpenID Connect `subject` value. It does not store a Google access token, refresh token, or raw ID token. An identity may also retain the provider email as non-authoritative display metadata; the stable subject is the link key.

Supported values:

```text
identity_type: LOCAL_PASSWORD | GOOGLE
```

Indexes:

```javascript
db.auth_identities.createIndex(
  { user_id: 1, identity_type: 1 },
  { unique: true }
)
db.auth_identities.createIndex(
  { provider: 1, subject: 1 },
  { unique: true, partialFilterExpression: { provider: "GOOGLE" } }
)
```

The application checks expiry and status. The TTL index is cleanup, not authorization.

### 8. USDA provider cache

#### 8.1 `usda_food_cache` — deployed

Current fields are `_id`, `cache_key` (string), `payload` (BSON binary containing raw USDA JSON response bytes) and `expires_at` (BSON Date). Search/detail both use 24-hour freshness. Earlier normalized `provider_cache` examples with 6-hour/7-day TTLs were design proposals, not the deployed collection.

```javascript
db.usda_food_cache.createIndex({ cache_key: 1 }, { unique: true })
db.usda_food_cache.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```

Reads require `expires_at > now`; TTL deletion is asynchronous. No permanent catalogue exists yet. The planned Phase 3 food database has a separate retention policy and must not inherit this expiry index.

#### 9.4 `serving_definitions`

Named servings are private shortcuts for a precise quantity of a USDA or owned custom food. They are definitions, not nutrition snapshots. Logging a serving still resolves the food and requires normal preview/confirmation.

```json
{
  "_id": { "$oid": "66f7ebe012ab34cd56ef7803" },
  "user_id": { "$oid": "66f7e68012ab34cd56ef7890" },
  "schema_version": 1,
  "version": 1,
  "label": "1 small bowl",
  "food_type": "CUSTOM",
  "custom_food_id": "66f7eb0012ab34cd56ef7899",
  "quantity": { "amount": { "$numberDecimal": "45" }, "unit": "g" },
  "food_state": "PREPARED",
  "created_at": { "$date": "2026-09-28T07:00:00.000Z" },
  "updated_at": { "$date": "2026-09-28T07:00:00.000Z" }
}
```

For a USDA serving, `food_type` is `USDA` and `provider_food_id` is a decimal-string FDC ID; `custom_food_id` is omitted. For a custom serving, `provider_food_id` is omitted. #### 10.4 Confirmation transaction

The confirmation transaction performs:

1. Read preview by `_id`, `user_id`, unexpired state, and secret hash.
2. Check for an existing group with the same user/idempotency key.
3. Insert the `food_log_groups` document.
4. Insert every `food_logs` item.
5. Mark the preview `CONSUMED` with `consumed_at`.
6. Commit all writes or none.

The maximum initial group size is 50 items.

#### 10.5 Corrections and deletion

Confirmed nutrition snapshots are never updated in place.

- Correcting any item creates a complete replacement group with `revision + 1` and `supersedes_group_id`.
- The previous group becomes `SUPERSEDED` while its item snapshots remain unchanged.
- User deletion marks the group `VOIDED` with `voided_at`; physical deletion is governed by a separate data-retention policy.
- Dashboard and normal history queries include only the latest `CONFIRMED` revision and exclude `SUPERSEDED` and `VOIDED` groups.

```javascript
db.food_log_groups.find({

  status: "CONFIRMED",
  $or: [
```

### 13. TTL policy

TTL cleanup is used only for finite-lifetime technical data.

| Collection | Expiry behavior |
|---|---|
| `usda_food_cache` | 24-hour deployed freshness; application check plus TTL |
| `food_log_previews` | Initially 15 minutes |
| `email_tokens` | Token-specific finite expiry |
| `sessions` | Session-specific finite expiry |

Rules:

- Every provider cache document has `expires_at`.
- No cache has a permanent or unlimited TTL.
- The application validates expiry before use because TTL deletion is asynchronous.
- Historical food logs, target versions, custom foods, meals, profiles, and health records are application data, not cache, and do not receive cache TTL indexes.

### 14. Transaction boundaries

Use MongoDB transactions only for invariants spanning multiple documents:

MongoDB Atlas provides the replica-set behavior required for transactions. Local MongoDB must also run as a single-node replica set; a standalone local MongoDB process is insufficient for transaction-path integration tests.

#### 14.1 Registration

- Insert `users`.
- Insert `auth_identities`.
- Insert verification `email_tokens` record.

Email transmission occurs after commit. Failure leaves a resendable unverified account.

#### 14.2 Target activation

- Confirm the proposed version belongs to the user.
- Mark the previous active version `SUPERSEDED`.
- Mark the proposed version `ACTIVE`.

The partial unique index guarantees no second active version.

#### 14.3 Food-group confirmation

- Validate and consume preview.
- Insert group.
- Insert all item snapshots.
- Commit all or none.

#### 14.4 Food-group correction

- Insert replacement group and replacement item snapshots.
- Mark old group `SUPERSEDED`.

#### 14.5 Password reset

- Atomically consume reset token.
- Replace Argon2id password hash.
- Revoke all active session families.

### 15. Optimistic concurrency

Mutable documents use a numeric `version`.

Example update:

```javascript
db.user_profiles.updateOne(
  {
    user_id: ObjectId("66f7e68012ab34cd56ef7890"),
    version: 4
  },
  {
    $set: {
      weight: { amount: NumberDecimal("71.80"), unit: "kg" },
```

If `matchedCount` is zero, return `409 Conflict` rather than overwriting another update.

- Missing `user_id` on user-owned data.
- Incorrect BSON types.
- Unsupported enum values.

- Invalid group item counts.
- Invalid cache expiry.

### 18. Backup, recovery, and retention

Phase 1 uses a MongoDB Atlas Free cluster (`M0`) with no application-managed backups. Atlas-managed snapshots and point-in-time recovery are not available on this tier, and no `mongodump`-based replacement is in scope.

Accordingly, data recovery after accidental deletion, application defects, account compromise, or an Atlas data-loss event is not guaranteed. There is no recovery point objective (RPO) or recovery time objective (RTO) for this initial configuration. This is an explicit trade-off accepted for local development and the initial low-risk use of the product.

Cache collections remain disposable and can be rebuilt. Credentials and application data must never be copied into logs or CI artifacts.

#### 18.1 Food-history compaction

Exact `food_log_groups` and `food_logs` remain available for 90 days after confirmation. A scheduled compaction job first creates/verifies an immutable daily nutrition summary for the user and Tracking Day, then removes detailed group/item history. After compaction, historical nutrition remains available through the daily summaries, but individual foods and servings cannot be shown, corrected, or deleted. The job must be idempotent and must never remove detail before its summary is successfully committed.

#### 18.2 Account deletion

Users may request account deletion. The request requires recent re-authentication: local-password users confirm with their password; Google-only users re-authenticate through Google. The account enters a 30-day deletion-pending period by default and is immediately signed out everywhere. At the end of that period, Core permanently deletes user-owned identity, profile, preference, target, food, meal, health, session, token, and summary documents, except information whose retention is legally required. Provider-cache entries are shared/disposable and do not contain user-owned account data. Until a future export feature is explicitly added, deletion does not imply a downloadable data export.

`account_deletions` holds one lifecycle record per user (`PENDING` or `CANCELLED`) with `requested_at`, `purge_after`, optional `cancelled_at`, and `updated_at`. Core's hourly purge worker deletes only a `PENDING` record whose `purge_after` has elapsed, in the same transaction as the user-owned documents. Cancellation before that deadline restores the user to `ACTIVE` and marks the lifecycle record `CANCELLED`.

## Phase 2 — released storage additions

Phase 2 additive recipe storage: owned `meals` documents may include `recipe_servings` (positive decimal text) and `preparation` (text). Existing documents without a yield remain ordinary meals. The existing components hold ingredient references, quantities, units, and states. Recipe edits use the meal version guard. Confirmed food groups/items retain the actual scaled quantities and nutrient snapshots; they never read live recipe data to calculate historical totals. No collection rewrite is required.

Nutrient keys accept `^[A-Z][A-Z0-9_]{0,39}$`, including `VITAMIN_B6`/`VITAMIN_B12` while excluding unsafe MongoDB path/operator characters.

`wellness_records` stores owned WATER/WEIGHT/ACTIVITY entries with `_id`, `user_id`, optimistic `version`, canonical Decimal128 `amount`, unit (`ml`, `kg`, or `min`), UTC `logged_at`, and immutable-context `tracking_day`, `timezone`, and `daily_reset_time`. Activity adds name, intensity, optional Decimal128 `estimated_kcal`, and notes. Removal soft-deletes with `deleted_at` and increments version. Editing an unchanged instant preserves its original Tracking Day context. Index: `{user_id:1, tracking_day:1, kind:1, _id:-1}`.

`wellness_settings` stores one document per user (unique `user_id`) with optimistic `version` and optional Decimal128 `water_target_ml`. Missing/null target means no user-selected goal; no target is inferred. Both collections are purged by account deletion.

`health_item_schedule_versions` additionally stores `month_days` (1–31), `effective_to_date`, and `MONTHLY`/`PAUSED` frequency values. A replacement closes the previous version without extending an already earlier end date. Replacements start on a future calendar date, preserving past and today's occurrences/actions. History reads are owner-scoped and paginated by descending schedule version. No destructive migration of existing daily/weekly schedules is required.

Recipe portion overrides retain separate provider and user-override nutrient snapshots through the existing preview/confirmation model; edits to the recipe definition do not rewrite confirmed food history.

## Phase 3 — proposed data model, not deployed

### Shared food database and catalogue

Reuse Atlas with an environment-isolated logical food database (base-name proposal: `atethat_foods`; final environment naming/credentials TBD). Core remains its only application client. A candidate `foods` collection has unique provider + provider-food-ID identity, normalized searchable names/state, completeness status, quantity/serving basis, supported nutrient amounts/units, attribution, fetch/normalization versions and meaningful usage metadata. These are design candidates, not finalized BSON schemas.

Preserve same-name different-ID foods. Partial search records must be distinguished from full details. No images or complete raw provider responses in the new catalogue; bounded imports only. No inactivity TTL. Freshness/refetch is independent of retention. Measure document plus index sizes against the proposed 20 MB budget, then approve enforcement and storage-full behaviour.

### Quotas, access and cleanup

Candidate usage/reservation records need a unique user + quota-day key and atomic reserve/settle/refund semantics; reset boundary/accounting remain open. Track upstream request budgets independently across search/detail/refresh. Expired reservations need safe reconciliation, not premature reset allowing concurrent overshoot. Treat application-wide and per-user limits separately.

Shared records are source data, not user-editable foods. Custom foods/recipes and overrides remain owner-scoped in the application database; account deletion must purge future user-specific quota/grant/job data but not shared source foods. Cleanup needs dry-run candidates and reference-safe handling for favourites, personal servings and recipe components. Confirmed diary snapshots and daily summaries are never catalogue-cleanup targets. Plan a safe migration alongside the disposable 24-hour cache.

Reusable cache/rate-limit keys must use `atethat:<environment>:v1:...` namespaces (with user identity where needed); this is not authorization or a reason to add Redis.

### Assisted input, exports and agents

Possible proposal/upload, export-job and agent-grant/audit entities require a reviewed privacy/retention schema before creation. Keep provider costs, upload deletion and bounded job storage explicit; avoid copying health payloads into audit records. Revocation and minimum agent audit are Phase 3 requirements, independent of a later global audit pipeline. Exports preserve decimal/time/provenance and cannot reconstruct compacted detail. See [Phase 3 backlog](PHASE_3_BACKLOG.md).

## Phase 4 and later — conditional storage

Outbox/jobs and wider audit/analytics collections are [future platform work](PHASE_4_BACKLOG.md), not currently deployed schemas. Recovery/backups require separate approval. No barcode storage is planned.
