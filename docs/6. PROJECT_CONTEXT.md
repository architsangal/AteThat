## 2. Product intent and boundaries

AteThat is a responsive nutrition and personal health-tracking web application. It is designed to feel premium, warm, minimal, and trustworthy in both light and dark themes.

- Tagline: **AteThat — Know what nourishes you.**
- Nutrition focuses on calories/energy first, then routine nutrients.
- It is a tracker, not a medical advice, prescription, diagnosis, or dosage-recommendation system.
- Phase 1 has normal users only. There is no separate admin product or role model yet.
- USDA FoodData Central and user-saved food data are the only food sources in Phase 1. Do not add a general food database without an explicit decision.
- FDA Daily Values are shown only as transparent, general benchmarks—not personalized nutrition prescriptions.

## 3. Confirmed engineering decisions

| Area | Decision |
|---|---|
| Repository | Existing repository is the monorepo. Applications own their code; no hidden runtime helper sharing between services. |
| Frontend | React, TypeScript, Vite static application. Google Stitch exports are visual references only, not feature requirements. |
| Backend | Public Go API Service and private Go Core Service, connected with gRPC/Protocol Buffers. |
| Data ownership | Core is the only service that accesses MongoDB, USDA, and SMTP. |
| Database | MongoDB Atlas M0 initially. Database selection is configuration-driven so a future self-hosted MongoDB can be used without changing product logic. |
| Time | Persist instants in UTC. Store the user-selected default IANA timezone separately. Users manually change it when travelling. |
| Food retention | Keep detailed food records for three months; preserve daily/monthly aggregates afterward. |
| Cache | No permanent cache entries. Maximum TTL is 15 days. |
| Pagination | All applicable list APIs require pagination. |
| Deletes | Account deletion has a 30-day cancellation period before permanent purge. |
| Email | Dedicated Gmail account via SMTP app password for low-volume transactional email. Mailpit remains local-only. |
| Google | Google sign-in and explicit linking are supported. A linked Google email must exactly match the AteThat account email. |
| Secrets | Never commit real credentials, app passwords, OAuth secrets, signing material, access tokens, or production environment files. |

## 4. Authentication behavior implemented locally

- Email/password registration requires email verification.
- Passwords are one-way Argon2id hashes. They cannot be recovered from the database.
- Access tokens are short-lived and held in browser memory. Refresh tokens are rotating, opaque, `HttpOnly` cookies.
- The frontend redirects to login when a protected request determines the session is invalid or expired.
- Forgot-password behavior is intentionally account-aware:
  - Email/password account: email a password-reset link.
  - Google-only account: email a one-time secure link that lets the user set a local password and sign in; Google sign-in continues to work.
- Google sign-in can create/sign into a Google account. A normal authenticated user may link Google only when the returned verified Google email matches their existing normalized AteThat email.
- Profile responses include `has_google_identity`. This must remain present on both `GET /profile` and `PATCH /profile`; otherwise a profile save can falsely show the Google-link button until refresh.
- Chrome password-saving is requested through standards-based password credential support where the browser permits it. Browser settings ultimately control the prompt.

## 5. Current local implementation

The local Compose stack includes MongoDB, Mailpit, Core, and API. The frontend runs through Vite at `http://localhost:5173`; API is exposed locally at `http://localhost:18080`.

Implemented Phase 1 journeys:

- Registration, verification, login, logout, refresh, password reset, and account deletion/cancellation.
- Gmail SMTP support via local ignored environment configuration; Mailpit for local-only capture.
- Google OAuth sign-in, linking, and Google-based deletion verification configuration.
- User profile, default timezone, date of birth, daily reset time, theme selection, and units.
- USDA search, custom foods, named servings, favourites/recent/frequent foods, reusable meals.
- Grouped food-log drafting, review, explicit confirmation, correction, history, and analysis.
- FDA general benchmark proposal/review/activation and target history.
- Medication and supplement schedules, scheduled occurrences, and recorded actions.
- Responsive layouts, custom date picker, shared select-chevron treatment, light/dark themes, route animations, and shared validation/status message styling.

The latest UI consistency work standardized direct panel and page feedback spacing. `form-message` deliberately has no intrinsic outer margin so it works inside grid forms; panels that render it as a direct sibling now supply the shared visual gap. Preserve this pattern when adding new feedback states.

## 6. Local configuration and safe defaults

Use `make local-config` to generate local cryptographic values and then use the ignored `deploy/local/.env` file. The committed `deploy/local/.env.example` contains placeholders only.

Important local environment values:

- `SMTP_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`
- `USDA_API_KEY` (`DEMO_KEY` is intentionally rate-limited)
- `FRONTEND_ORIGIN`
- signing/public-key/internal-service values created by local setup

For local Google OAuth, the redirect URI is:

```text
http://localhost:18080/api/v1/auth/google/callback
```

The frontend enables the Google button only when `VITE_GOOGLE_SIGNIN_ENABLED=true` in the ignored `apps/web/.env.local` file.

## 7. Deployment direction — not deployed yet

The product is intentionally local-first. Deployment should happen only after final local end-to-end QA.

Target architecture:

```text
Cloudflare Pages (React frontend)
        |
        v
Caddy on a KVM (HTTPS / reverse proxy)
        |
        v
API Service -> private gRPC -> Core Service -> MongoDB Atlas M0
                                      |-> USDA FoodData Central
                                      `-> Gmail SMTP
```

Preferred public URL model for multiple future projects:

```text
atethat.example.com            frontend
api.atethat.example.com        AteThat API
rollercoaster.example.com      a future separate project
```

Product-specific subdomains are preferred over a `/AteThat/` path because they simplify static hosting, SPA routing, OAuth redirect URIs, cookies, and Caddy routing.

Production work still required:

1. Purchase/configure domain, Cloudflare DNS, and KVM.
2. Add production Compose and Caddy configuration; current Compose files are local development assets.
3. Create MongoDB Atlas project/database user/network allow-list for the KVM IP.
4. Add production-only environment values on the server; set `COOKIE_SECURE=true`.
5. Set Cloudflare Pages build variables: `VITE_API_BASE_URL` and `VITE_GOOGLE_SIGNIN_ENABLED=true`.
6. Add production Google OAuth origin and exact HTTPS redirect URI.
7. Configure Gmail SMTP on the server; do not use Mailpit in production.
8. Add health checks, log rotation, monitoring/alerting, and a clear Atlas M0 data-loss policy.

## 9. Remaining work and next recommended actions

### Before declaring local Phase 1 QA complete

1. Run an end-to-end user regression test: signup, verification, email/password login, session expiry redirect, password reset, Google login/linking, food logging, history, analysis, targets, health items, settings, and deletion/cancellation.
2. Repeat the visual check at mobile, tablet, and desktop widths for every route; specifically inspect overflow, feedback spacing, date pickers, and native control fallbacks.
3. Use a personal USDA key for broader provider testing if the `DEMO_KEY` quota becomes restrictive.
4. Review all uncommitted work before the next commit; keep generated protobuf changes aligned with their `.proto` source.

### Before production

1. Implement and review production Compose/Caddy artifacts.
2. Decide the canonical domain/subdomain names.
3. Complete real-domain OAuth and SMTP tests.
4. Choose and install minimum monitoring (for example Uptime Kuma plus Docker log rotation).
