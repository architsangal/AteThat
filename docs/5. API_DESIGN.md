## 1. Purpose and boundaries

This document defines the browser-facing REST contract for AteThat. It specifies request and response shapes, authentication, validation, pagination, concurrency, errors, and the mapping to the private API-to-Core gRPC boundary.

It is **not** a database API. The browser calls only the public API Service. The API Service validates HTTP input and identity, then calls the Core Service through private gRPC. Only Core accesses MongoDB, USDA, or the email provider.

```text
Browser  -- HTTPS /api/v1 -->  API Service  -- private gRPC -->  Core Service
                                                               ├─ MongoDB
                                                               ├─ USDA
                                                               └─ Gmail SMTP
```

The generated OpenAPI document and Protocol Buffer files will become the implementation-level source of truth. They must conform to this design rather than introduce different public semantics.

## 2. Universal conventions

### 2.1 Authentication

Protected endpoints require:

```http
Authorization: Bearer <access_token>
```

- Access tokens are short-lived and kept in browser memory.
- Refresh tokens are opaque, rotated tokens delivered only in a `Secure`, `HttpOnly`, `SameSite=Lax` cookie. They never appear in JSON, logs, URLs, or browser storage.
- `POST /auth/refresh` reads the refresh-token cookie and returns a replacement access token. The browser must send `credentials: include` for this call.
- The user identity always comes from the validated access token. Requests never contain a trusted `user_id` field.
- A request with no valid access token returns `401 UNAUTHENTICATED`; a resource owned by another user is returned as `404 RESOURCE_NOT_FOUND`.

### 2.2 Types, time, quantities, and IDs

| Concept | Wire representation | Example |
|---|---|---|
| Resource ID | MongoDB ObjectId as 24-character lowercase hex string | `"66f7ec8012ab34cd56ef7804"` |
| Instant | RFC 3339 with `Z` or an explicit UTC offset | `"2026-09-28T02:30:00Z"` |
| Date | ISO 8601 date | `"2026-09-28"` |
| Local time | 24-hour `HH:mm` | `"04:00"` |
| Timezone | IANA timezone name | `"Asia/Kolkata"` |
| Decimal amount | JSON string, never binary floating-point | `"72.50"`, `"200"` |
| Enum | Uppercase snake case | `"BREAKFAST"` |

The Core Service converts all persisted instants to UTC. It separately records user timezone and Tracking Day context where historical interpretation requires it. The API does not guess a timezone for an ambiguous timestamp. The UI formats instants using the user’s manually managed default timezone and labels meaningful times with an abbreviation/offset such as `IST (UTC+05:30)` or `GMT+05:30`.

### 2.3 Nutrient map

All nutrient payloads use this canonical map. Missing data is explicit, rather than silently treated as zero.

```json
{
  "ENERGY": { "status": "KNOWN", "amount": "260", "unit": "kcal" },
  "PROTEIN": { "status": "KNOWN", "amount": "5.38", "unit": "g" },
  "FIBER": { "status": "UNKNOWN", "amount": null, "unit": "g" }
}
```

`status` is `KNOWN` or `UNKNOWN`. The allowed nutrient keys and units are controlled by the versioned nutrition reference set; clients must render unknown nutrients distinctly from a genuine amount of zero.

### 2.4 Request metadata

Every response contains a request ID:

```http
X-Request-Id: 01J9Q8ZQK6R4YDPSHTB8XEK7ZZ
```

Clients may supply `X-Request-Id` using a safe identifier; otherwise API generates one. Do not place personal, medical, credential, or food data in it.

For retry-sensitive creation, clients also supply:

```http
Idempotency-Key: 4bd707b9-b5d3-4b64-9f75-4da920a1cfc4
```

The key is a UUID generated once per user action and reused only when retrying that same action. In Phase 1 it is mandatory for food-group confirmation and may be applied to other transaction-producing creates as implementation hardening.

### 2.5 Pagination

Any endpoint returning a growable collection supports keyset pagination:

```text
limit   optional, default 20, minimum 1, maximum 100
cursor  optional opaque cursor returned by the previous response
```

Example response:

```json
{
  "items": [],
  "page": {
    "next_cursor": "eyJ2IjoxLCJzY29wZSI6Im1lYWxzIn0...",
    "has_more": true
  }
}
```

The cursor is opaque and signed. It is bound to the authenticated user, endpoint scope, filters, and sort order. A client must not construct, decode, reuse with different filters, or treat it as a provider token. Invalid/expired/mismatched cursors return `400 INVALID_CURSOR`.

### 2.6 Optimistic concurrency

Mutable resources return a positive integer `version`. `PATCH` and similar update operations require the client’s last observed version:

```json
{ "version": 4, "display_name": "Archit" }
```

If the document has changed, API returns `409 VERSION_CONFLICT` with the current safe version. The client refreshes the resource and asks the user to resolve any meaningful conflict. Confirmed food history is not patched in place; see section 8.

### 2.7 Error format and HTTP status mapping

All errors use `application/problem+json`:

```json
{
  "type": "https://errors.atethat.invalid/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "code": "VALIDATION_FAILED",
  "detail": "One or more fields are invalid.",
  "request_id": "01J9Q8ZQK6R4YDPSHTB8XEK7ZZ",
  "field_errors": [
    {
      "field": "items[0].quantity.amount",
      "code": "MUST_BE_POSITIVE",
      "message": "Quantity must be greater than zero."
    }
  ]
}
```

| Status | Code examples | Meaning |
|---|---|---|
| 400 | `INVALID_CURSOR`, `INVALID_TIMESTAMP` | Malformed request semantics |
| 401 | `UNAUTHENTICATED`, `SESSION_EXPIRED` | Missing/invalid authentication |
| 403 | `EMAIL_NOT_VERIFIED` | Authenticated but account cannot perform this action |
| 404 | `RESOURCE_NOT_FOUND` | Resource absent or not owned by caller |
| 409 | `VERSION_CONFLICT`, `IDEMPOTENCY_KEY_REUSED` | State or concurrency conflict |
| 410 | `PREVIEW_EXPIRED`, `TOKEN_EXPIRED` | Valid identifier for an expired/consumed temporary resource |
| 422 | `VALIDATION_FAILED`, `INVALID_SCHEDULE` | Well-formed body fails business validation |
| 429 | `RATE_LIMITED` | Endpoint-specific limit exceeded |
| 502 | `FOOD_PROVIDER_FAILURE`, `EMAIL_DELIVERY_FAILURE` | Upstream dependency failed |
| 503 | `CORE_UNAVAILABLE`, `FOOD_PROVIDER_UNAVAILABLE` | Temporary service dependency outage |

Responses never reveal password hashes, raw tokens, session records, database details, secrets, or raw third-party error bodies.

## 3. Shared public schemas

### 3.1 Authenticated user and session response

```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in_seconds": 900,
  "user": {
    "id": "66f7e68012ab34cd56ef7890",
    "email": "archit@example.com",
    "email_verified": true,
    "status": "ACTIVE"
  }
}
```

The raw refresh token is deliberately absent. A successful login/refresh also sets its cookie through `Set-Cookie`.

### 3.2 Food reference and quantity

```json
{
  "food_reference": {
    "type": "USDA",
    "provider_food_id": "171077",
    "custom_food_id": null
  },
  "quantity": { "amount": "200", "unit": "g" },
  "food_state": "COOKED"
}
```

`type` is `USDA` or `CUSTOM`. Exactly one reference ID must be supplied. `food_state` is one of the states supported by the normalizer (for example `RAW`, `COOKED`, `PREPARED`, `UNKNOWN`); an unsupported state returns validation error.

### 3.3 Food result and food-log item

```json
{
  "id": "66f7ed0012ab34cd56ef7805",
  "position": 0,
  "food_source": {
    "type": "USDA",
    "provider_food_id": "171077",
    "custom_food_id": null,
    "name": "Rice, white, cooked"
  },
  "quantity": { "amount": "200", "unit": "g" },
  "food_state": "COOKED",
  "final_nutrition": { "ENERGY": { "status": "KNOWN", "amount": "260", "unit": "kcal" } }
}
```

Provider result data is normalized into this app contract. It is never a direct USDA payload.

## 4. Identity and account API

All identity request bodies have an enforced size limit. Passwords are accepted only in request bodies over TLS; they must never be placed in query strings or logs.

### 4.1 Register

`POST /auth/register`

```json
{
  "email": "Archit@example.com",
  "password": "user-chosen-secret",
  "display_name": "Archit",
  "timezone": "Asia/Kolkata"
}
```

`email`, `password`, `display_name`, and `timezone` are required. API normalizes email for uniqueness, creates the account in `PENDING_EMAIL_VERIFICATION`, hashes the password with Argon2id, and sends a verification email.

Response: `202 Accepted`

```json
{ "message": "If registration can be completed, a verification email has been sent." }
```

The deliberately generic message prevents account discovery. Password length/composition policy is implemented consistently in API and Core; exact values belong in the security configuration, not the client.

### 4.2 Verify or resend email verification

`POST /auth/verify-email`

```json
{ "token": "raw-token-from-email" }
```

Response: `200 OK`

```json
{ "email_verified": true }
```

`POST /auth/resend-verification`

```json
{ "email": "archit@example.com" }
```

Response is always `202 Accepted` with the same generic message as registration. Verification tokens are single-use, hashed at rest, finite, and replaced by a resend.

### 4.3 Local login, Google Sign-In, refresh, and logout

`POST /auth/login`

```json
{ "email": "archit@example.com", "password": "user-chosen-secret" }
```

Response: `200 OK`, session response from section 3.1, plus refresh cookie. Unverified accounts receive `403 EMAIL_NOT_VERIFIED`; the response may include a safe `can_resend_verification` boolean.

`GET /auth/google/start?return_to=/dashboard` starts the Google OAuth 2.0/OpenID Connect authorization-code flow with PKCE. API validates `return_to` against a small allowlist of in-app paths, creates a short-lived one-time state/nonce record, and redirects the browser to Google. It never accepts an arbitrary callback URL.

`GET /auth/google/callback?code=...&state=...` consumes the one-time state, exchanges the code server-side, validates Google issuer, audience, expiry, nonce, and stable subject, then creates the AteThat session and refresh cookie. It redirects only to the configured frontend origin/path. The browser never receives a Google client secret or provider token.

On first Google sign-in, Core creates a new account when no verified existing account has the same normalized email. If an account already exists, Core requires explicit authenticated linking rather than silently merging identities based only on email. Phase 1 does not auto-link accounts.

`GET /account/identities/google/link/start` is available only to an already authenticated user. It starts the same backend-managed Google flow with a state record marked as an identity-link operation. Its callback attaches the Google subject only after verifying it is not already linked to another AteThat account. This is the supported way for an existing local-password user to add Google login.

`POST /auth/refresh`

No JSON body. Reads the refresh cookie, rotates it, and responds with section 3.1. The endpoint must reject cross-site misuse using cookie policy plus CSRF/origin protection appropriate to the deployed frontend/API origins.

`POST /auth/logout`

No body. Requires access token or valid refresh cookie; revokes the current session family and clears the cookie. Response: `204 No Content` even if the cookie is already invalid.

### 4.4 Password reset

`POST /auth/forgot-password`

```json
{ "email": "archit@example.com" }
```

Response: `202 Accepted`

```json
{ "message": "If an eligible account exists, password reset instructions have been sent." }
```

`POST /auth/reset-password`

```json
{
  "token": "raw-token-from-email",
  "new_password": "another-user-chosen-secret"
}
```

Response: `204 No Content`. Core consumes the token exactly once, changes the Argon2id hash, and revokes every active session family for that user.

### 4.5 Delete account

`POST /account/deletion-request` requires recent re-authentication. A local-password identity sends:

```json
{ "method": "LOCAL_PASSWORD", "password": "user-chosen-secret" }
```

For a Google-only user, the browser completes the server-managed Google re-authentication flow; it never posts a Google token to this endpoint. API returns `202 Accepted`, immediately revokes active sessions, and returns the deletion-pending end time. Core permanently removes user-owned data only after the configured grace period. The grace period and cancellation endpoint must be fixed before implementation.

## 5. Profile and preferences API

### 5.1 Profile

`GET /profile` returns `200 OK`:

```json
{
  "id": "66f7e80012ab34cd56ef7894",
  "version": 4,
  "display_name": "Archit",
  "date_of_birth": "1998-04-12",
  "sex": "MALE",
  "height": { "amount": "178.0", "unit": "cm" },
  "weight": { "amount": "72.50", "unit": "kg" },
  "activity_level": "MODERATE",
  "goal": "MAINTAIN",
  "timezone": "Asia/Kolkata",
  "updated_at": "2026-09-29T08:00:00Z"
}
```

`PATCH /profile` accepts only supplied mutable fields and requires `version`:

```json
{
  "version": 4,
  "weight": { "amount": "71.80", "unit": "kg" },
  "activity_level": "ACTIVE"
}
```

Response: updated profile. A profile change does not retroactively modify existing nutrition-target versions, food logs, or Tracking Day snapshots. A client can explicitly request a new target calculation.

### 5.2 Preferences

`GET /preferences` returns:

```json
{
  "id": "66f7e85012ab34cd56ef7895",
  "version": 3,
  "daily_reset_time": "04:00",
  "unit_system": "METRIC",
  "dashboard_nutrients": ["ENERGY", "PROTEIN", "CARBOHYDRATE", "FAT", "FIBER"]
}
```

`PATCH /preferences` requires `version` and accepts `daily_reset_time`, `unit_system`, and ordered `dashboard_nutrients`. A new reset time affects future Tracking Day calculation; confirmed logs retain their historical reset-time snapshot.

## 6. Nutrition target API

### 6.1 Calculate a proposed target version

`POST /nutrition/targets/calculate`

```json
{
  "profile_version": 4,
  "effective_from_tracking_day": "2026-09-30"
}
```

The Core Service selects its active, application-controlled reference set, calculates a complete proposal, and returns a `PROPOSED` version:

```json
{
  "id": "66f7e95012ab34cd56ef7897",
  "status": "PROPOSED",
  "revision": 2,
  "profile_version": 4,
  "reference_set": { "key": "INDIA_REFERENCE_SET", "version": "2026.1" },
  "source_attribution": {
    "name": "Reference dataset name",
    "publisher": "Reference publisher",
    "version": "2026.1",
    "information_url": "https://example.invalid/reference"
  },
  "calculation_version": "target-engine-v1",
  "effective_from_tracking_day": "2026-09-30",
  "targets": {
    "ENERGY": { "reference_value": "2300", "active_value": "2300", "unit": "kcal", "is_manual_override": false },
    "PROTEIN": { "reference_value": "110", "active_value": "110", "unit": "g", "is_manual_override": false }
  }
}
```

`source_attribution` is returned for every proposed, active, and historical target version. The frontend shows its name beside the recommendation and exposes publisher/version/information URL through an information icon or popover. It explains the dataset behind the value without representing the value as medical advice.

### 6.2 Read, accept, reject, and list target versions

`GET /nutrition/targets` returns active and any outstanding proposed version; it is not paginated because the result is bounded.

`POST /nutrition/targets/{version_id}/accept`

```json
{
  "effective_from_tracking_day": "2026-09-30",
  "overrides": {
    "PROTEIN": { "active_value": "130", "override_reason": "Personal target" }
  }
}
```

Core atomically activates the accepted complete version and supersedes the previous active version. Values not supplied in `overrides` retain the proposal value. Response: activated target version, `200 OK`.

`POST /nutrition/targets/{version_id}/reject` takes an empty object and returns `204 No Content`.

`GET /nutrition/targets/history?limit=20&cursor=...` returns a paginated list ordered by revision descending.

## 7. Food catalogue, custom food, favourites, and meals API

### 7.1 USDA food search and detail

`GET /foods/search?q=rice&food_state=COOKED&limit=20&cursor=...`

- `q` is required, normalized, and limited in length.
- `food_state` is optional and affects result suitability; it does not rewrite provider data.
- Response is paginated. Provider pagination is translated to AteThat’s cursor format.

```json
{
  "items": [
    {
      "food_reference": { "type": "USDA", "provider_food_id": "171077", "custom_food_id": null },
      "name": "Rice, white, cooked",
      "food_state": "COOKED",
      "base_quantity": { "amount": "100", "unit": "g" },
      "nutrients": { "ENERGY": { "status": "KNOWN", "amount": "130", "unit": "kcal" } }
    }
  ],
  "page": { "next_cursor": null, "has_more": false }
}
```

`GET /foods/provider/{provider_food_id}` returns one normalized USDA food detail. It can be served from an unexpired cache, but cache lifetime is never more than 15 days. If provider/cached data is not available, returns `503 FOOD_PROVIDER_UNAVAILABLE`.

### 7.2 Custom foods

| Method | Path | Behaviour |
|---|---|---|
| GET | `/foods/custom` | Paginated, owned custom foods; excludes soft-deleted items |
| POST | `/foods/custom` | Create custom food |
| GET | `/foods/custom/{custom_food_id}` | Read owned custom food |
| PATCH | `/foods/custom/{custom_food_id}` | Update with `version` |
| DELETE | `/foods/custom/{custom_food_id}` | Soft-delete; preserves existing historical snapshots |

Create example:

```json
{
  "name": "My Protein Shake",
  "description": "Home recipe",
  "food_state": "PREPARED",
  "base_quantity": { "amount": "300", "unit": "ml" },
  "nutrients": {
    "ENERGY": { "status": "KNOWN", "amount": "280", "unit": "kcal" },
    "PROTEIN": { "status": "KNOWN", "amount": "32", "unit": "g" }
  }
}
```

Response: `201 Created` with the custom food and `Location: /api/v1/foods/custom/{id}`. A custom-food update must not mutate confirmed food-log snapshots.

### 7.3 Favourites, recent, and frequent foods

| Method | Path | Request/response |
|---|---|---|
| GET | `/foods/favourites` | Paginated favourites |
| POST | `/foods/favourites` | `{ "food_reference": { ... } }`; marks it favourite, idempotently |
| DELETE | `/foods/favourites/{food_key}` | Removes favourite; `food_key` is URL-safe canonical key such as `USDA:171077` |
| GET | `/foods/recent` | Paginated derived recent foods; optional bounded recency filters |
| GET | `/foods/frequent` | Paginated derived frequent foods; optional date-range filters |

Recent/frequent lists are derived only from visible confirmed food history; they do not expose another user’s data or include superseded/voided groups.

### 7.4 Meals

| Method | Path | Behaviour |
|---|---|---|
| GET | `/meals` | Paginated owned meals |
| POST | `/meals` | Create reusable meal definition |
| GET | `/meals/{meal_id}` | Read owned meal |
| PATCH | `/meals/{meal_id}` | Update definition with `version` |
| DELETE | `/meals/{meal_id}` | Soft-delete definition |
| POST | `/meals/{meal_id}/preview` | Create food-log preview from current components |

Create meal:

```json
{
  "name": "Weekday Breakfast",
  "components": [
    {
      "position": 0,
      "food_reference": { "type": "USDA", "provider_food_id": "171077", "custom_food_id": null },
      "quantity": { "amount": "200", "unit": "g" },
      "food_state": "COOKED"
    }
  ]
}
```

`POST /meals/{meal_id}/preview` accepts the shared logging inputs:

```json
{
  "logged_at": "2026-09-28T02:30:00Z",
  "meal_category": "BREAKFAST",
  "label": "Post-workout breakfast"
}
```

It uses the current meal components and returns exactly the preview shape in section 8. A saved meal is a reusable definition, not a historical nutrition record.

## 8. Food-log preview, confirmation, history, and correction API

### 8.1 Create preview

`POST /food-log-groups/preview`

```json
{
  "logged_at": "2026-09-28T02:30:00Z",
  "meal_category": "BREAKFAST",
  "label": "Post-workout breakfast",
  "items": [
    {
      "position": 0,
      "food_reference": { "type": "USDA", "provider_food_id": "171077", "custom_food_id": null },
      "quantity": { "amount": "200", "unit": "g" },
      "food_state": "COOKED",
      "user_override_nutrition": {}
    },
    {
      "position": 1,
      "food_reference": { "type": "CUSTOM", "provider_food_id": null, "custom_food_id": "66f7eb0012ab34cd56ef7899" },
      "quantity": { "amount": "300", "unit": "ml" },
      "food_state": "PREPARED",
      "user_override_nutrition": {}
    }
  ]
}
```

Rules:

- `items` has 1–50 entries and unique consecutive positions starting at 0.
- `logged_at` is an actual instant with `Z` or explicit offset. Core normalizes it to UTC and derives the Tracking Day using the user’s default timezone/reset-time policy.
- `meal_category` is `BREAKFAST`, `LUNCH`, `DINNER`, `SNACK`, or `OTHER`.
- `label` is optional, user-visible text with a bounded length.
- Override values must use the canonical nutrient schema. Final values are calculated server-side; a client cannot assert a final total.

Response: `201 Created`

```json
{
  "preview_token": "opaque-preview-id-and-secret",
  "expires_at": "2026-09-28T02:45:00Z",
  "group": {
    "logged_at": "2026-09-28T02:30:00Z",
    "tracking_day": "2026-09-28",
    "meal_category": "BREAKFAST",
    "label": "Post-workout breakfast",
    "item_count": 2,
    "items": [
      {
        "position": 0,
        "food_source": { "type": "USDA", "provider_food_id": "171077", "name": "Rice, white, cooked" },
        "quantity": { "amount": "200", "unit": "g" },
        "final_nutrition": { "ENERGY": { "status": "KNOWN", "amount": "260", "unit": "kcal" } }
      }
    ],
    "aggregate_final_nutrition": { "ENERGY": { "status": "KNOWN", "amount": "540", "unit": "kcal" } },
    "calculation_version": "nutrition-normalizer-v1"
  }
}
```

Preview is intentionally not historical storage. The opaque preview token is valid only for its owner and only for its short, finite expiry (initially 15 minutes).

### 8.2 Confirm preview atomically

`POST /food-log-groups/confirm`

Headers: `Idempotency-Key` is required.

```json
{ "preview_token": "opaque-preview-id-and-secret" }
```

Response: `201 Created` on first successful confirmation; `200 OK` plus the same resulting group when a safely repeated request uses the same idempotency key.

```json
{
  "id": "66f7ec8012ab34cd56ef7804",
  "root_group_id": "66f7ec8012ab34cd56ef7804",
  "revision": 1,
  "status": "CONFIRMED",
  "logged_at": "2026-09-28T02:30:00Z",
  "tracking_day": "2026-09-28",
  "meal_category": "BREAKFAST",
  "label": "Post-workout breakfast",
  "item_count": 2,
  "aggregate_final_nutrition": { "ENERGY": { "status": "KNOWN", "amount": "540", "unit": "kcal" } },
  "items": [
    {
      "id": "66f7ed0012ab34cd56ef7805",
      "position": 0,
      "food_source": { "type": "USDA", "provider_food_id": "171077", "name": "Rice, white, cooked" },
      "quantity": { "amount": "200", "unit": "g" },
      "food_state": "COOKED",
      "final_nutrition": { "ENERGY": { "status": "KNOWN", "amount": "260", "unit": "kcal" } }
    }
  ],
  "confirmed_at": "2026-09-28T02:35:00Z"
}
```

Core validates preview ownership, expiry, and secret; checks idempotency; writes one group and all item snapshots; marks the preview consumed; and commits all writes in one transaction. It returns no partial success.

Reusing an idempotency key with a different preview/body returns `409 IDEMPOTENCY_KEY_REUSED`. An expired/consumed preview returns `410 PREVIEW_EXPIRED` or `410 PREVIEW_CONSUMED`; the user creates a new preview.

### 8.3 Read history and one group

`GET /food-log-groups?tracking_day=2026-09-28&limit=20&cursor=...`

Allowed filter combinations:

- `tracking_day=YYYY-MM-DD`, or
- `from=RFC3339&to=RFC3339` where `from < to`.

Optional `meal_category` filters groups. The list is paginated by `logged_at DESC, id DESC`, returns summary group data, and includes normal visible history only: latest `CONFIRMED` groups, never `VOIDED` or `SUPERSEDED` revisions.

`GET /food-log-groups/{group_id}` returns the complete owned group with ordered immutable item snapshots. It can include historical revision metadata so the UI can explain a correction.

`GET /food-logs/{food_log_id}` returns one owned immutable item snapshot and its group summary.

### 8.4 Correct or delete confirmed history

`PATCH /food-logs/{food_log_id}` does **not** update an old snapshot. It accepts a corrected replacement request, for example:

```json
{
  "quantity": { "amount": "150", "unit": "g" },
  "reason": "Corrected serving size"
}
```

Core builds a replacement preview from the existing group, applies the explicit correction, and returns `201 Created` with the standard preview response from section 8.1. The caller must explicitly confirm that preview through `POST /food-log-groups/confirm`; Core then creates a new group revision and marks the previous group `SUPERSEDED`. The preview internally carries the source-group relationship, so the browser cannot choose or forge which historical group is superseded. Confirmed history is never silently mutated.

`DELETE /food-logs/{food_log_id}` maps to voiding its group (because group nutrition is atomic), not physical deletion of just one immutable item. Response: `204 No Content`. The UI must clearly state that the whole logged group is removed from normal totals. A later retention process governs physical deletion.

## 9. Health items, schedule versions, and occurrences API

### 9.1 Health items

| Method | Path | Behaviour |
|---|---|---|
| GET | `/health-items` | Paginated list; optional `active=true|false` filter |
| POST | `/health-items` | Create item plus first schedule version |
| GET | `/health-items/{health_item_id}` | Read item and current schedule summary |
| PATCH | `/health-items/{health_item_id}` | Update item; requires `version` |
| POST | `/health-items/{health_item_id}/deactivate` | Stop future occurrences without deleting prior events |

Create example:

```json
{
  "type": "SUPPLEMENT",
  "name": "Vitamin D",
  "dosage": { "amount_text": "1", "unit_text": "tablet" },
  "instructions": "As entered by the user",
  "notes": null,
  "start_date": "2026-09-28",
  "schedule": {
    "timezone": "Asia/Kolkata",
    "recurrence": {
      "frequency": "DAILY",
      "interval": 1,
      "weekdays": [],
      "local_times": ["08:00"]
    },
    "effective_from_date": "2026-09-28"
  }
}
```

`type` is `MEDICATION` or `SUPPLEMENT`. `frequency` is `DAILY` or `WEEKLY`; `interval` is a positive integer. `DAILY` requires no weekdays, while `WEEKLY` requires one or more `MON` through `SUN` values. `local_times` contains one or more `HH:mm` values.

When schedule fields change, Core creates a new `health_item_schedule_versions` document with the next version, closes the prior version’s effective range, and updates `current_schedule_version`. Past events remain tied to their existing schedule version.

`POST /health-items/{health_item_id}/deactivate`

```json
{ "version": 3, "end_date": "2026-10-31" }
```

Response is the inactive updated item. Deactivation does not delete past taken/skipped/rescheduled events.

### 9.2 Calculated occurrences and explicit actions

`GET /health-items/occurrences?from=2026-09-28T00:00:00Z&to=2026-10-05T00:00:00Z&limit=100&cursor=...`

The range is required and bounded by a server-configured maximum. Core expands schedule versions in the user’s schedule timezone and returns UTC instants plus their local interpretation. Unacted occurrences are calculated at read time; they are not persisted just because they exist.

```json
{
  "items": [
    {
      "occurrence_id": "opaque-stable-occurrence-identity",
      "health_item_id": "66f7ee0012ab34cd56ef7806",
      "schedule_version": 1,
      "scheduled_at": "2026-09-28T02:30:00Z",
      "scheduled_local": { "date": "2026-09-28", "time": "08:00", "timezone": "Asia/Kolkata" },
      "status": "SCHEDULED"
    }
  ],
  "page": { "next_cursor": null, "has_more": false }
}
```

`status` can be calculated `SCHEDULED`/`MISSED`, or persisted `TAKEN`/`SKIPPED`/`RESCHEDULED`.

`PUT /health-items/occurrences/{occurrence_id}`

```json
{
  "status": "TAKEN",
  "completed_at": "2026-09-28T02:35:00Z",
  "notes": ""
}
```

For `SKIPPED`, `completed_at` is omitted. For `RESCHEDULED`, include `rescheduled_to` as an RFC 3339 instant. The endpoint performs an idempotent upsert of the owned occurrence event, validates that occurrence ID against the server-derived schedule, and returns the persisted event. It must reject a foreign, invalid, or out-of-schedule occurrence identity.

## 11. Private gRPC contract

The REST API is the only public interface. gRPC is private to the service network and uses Protocol Buffers. It has domain-oriented methods, never generic document access.

|---|---|
| `IdentityService` | `Register`, `VerifyEmail`, `ResendVerification`, `Login`, `StartGoogleSignIn`, `CompleteGoogleSignIn`, `RefreshSession`, `Logout`, `RequestPasswordReset`, `ResetPassword`, `RequestAccountDeletion` |

## 13. Security, limits, and compatibility rules

- HTTPS is mandatory outside local development. CORS permits only configured AteThat frontend origins and never a wildcard with credentials.
- API validates content type, request-size limit, JSON shape, field length, enum values, timestamps, decimal strings, and access ownership before invoking Core.
- Rate limits are endpoint-specific. Login, register, resend verification, and password-reset requests have stricter IP and account/email safeguards. Public response messages remain enumeration-resistant.
- Browser-visible errors are safe. Structured logs contain the request ID and error code, but never passwords, tokens, raw email-reset/verification links, access tokens, refresh tokens, credentials, or full sensitive request bodies.
- The maximum 50 items per food-group preview protects transaction duration and resource use. List endpoints default to 20 and never exceed 100 items.
- `/api/v1` is the compatibility boundary. Backward-compatible fields may be added; changing/removing semantics or required fields requires a new API version. Existing enum additions must be handled defensively by clients.
- The server owns security- and history-critical data: authenticated user ID, database IDs, timestamps ultimately persisted in UTC, Tracking Day metadata, provider snapshots, calculated totals, versions, and idempotency outcome.

## 14. Implementation acceptance checks

Before exposing the API, contract tests must verify at least:

1. A user cannot read or mutate another user’s resource by guessing an ID or changing a body field.
2. UTC conversion and Tracking Day derivation are correct around the configured reset time and timezone changes.
3. Decimal quantity/nutrition handling never depends on binary floating point.
4. Cursor pagination is deterministic, bound to user/filters, and has no duplicates or omissions across a normal continuation.
5. A multi-food confirmation with the same idempotency key returns exactly one group and all-or-none item snapshots.
6. An expired, consumed, or foreign preview cannot be confirmed.
7. A custom food, meal, profile, preference, or health-item stale update returns `409 VERSION_CONFLICT`.
8. Food corrections create revision history; no confirmed snapshot is overwritten in place.
9. Password reset revokes existing sessions; raw secrets cannot be recovered from a database dump or normal logs.
10. Schedule changes create a new schedule version and old occurrence events remain correctly interpretable.
